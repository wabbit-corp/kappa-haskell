# Unified `derive`, canonical evidence, and lawful standard structures

## Ready-to-insert changes for `Spec(108).md`

This patch replaces the earlier unified-`derive` proposal. It is written against `Spec(108).md` and deliberately preserves
`Eq` and `Equiv` as separate selected structures. `Eq` does **not** refine `Equiv`. The standard `Eq -> Equiv` bridge becomes
a fallback instance so that a direct non-equality `Equiv` instance may replace it without overlap.

Normative keywords in this file have their ordinary specification force. Numbered headings below are application
instructions rather than proposed final section numbers; renumber the merged specification mechanically.

The patch has six load-bearing ideas:

1. `derive` is one expected-type-directed elaboration protocol used by expressions, instance bodies, member defaults,
   supertrait defaults, declaration-level deriving, and generated proof obligations.
2. A trait may carry an independently checked `evidence uniqueness` certificate. Such evidence may be constructed and
   transformed by ordinary source functions without sacrificing coherence.
3. Ordinary traits without such a certificate remain **sealed-coherent**. Their evidence is first-class to consume, pass,
   store, and return, but fresh implementations are introduced only by coherence-governed instance forms.
4. `forall` retains its existing meaning as an implicit quantity-`0` Pi. Computational domains use ordinary arrows.
5. Proof search is proof-producing, deterministic, logically bounded, and path-sensitive unless an independent h-level fact
   justifies proof irrelevance.
6. Semantic evidence identity is distinct from exact proof-artifact identity and audit provenance.

## 2. Surface grammar and parsing

### 2.1 Amend §5.2, “Keywords”

Add `fallback`, `evidence`, and `uniqueness` to the contextual soft-keyword list. They are keywords only in the declaration
positions introduced by this patch.

### 2.2 Add derivation expressions

```text
deriveExpr ::= 'derive'
             | 'derive' '(' type ')'

atom ::= ... | deriveExpr
```

`derive (T)` is parsed as one atomic expression, not as application of a term named `derive`.

### 2.3 Amend the trait-member grammar

```text
traitMember ::=
      memberName ':' type
    | 'let' memberName [':' type] '=' expr
    | 'derive' memberName ':' type
    | evidenceUniquenessClause

evidenceUniquenessClause ::=
    'evidence' 'uniqueness' '=' expr
```

The prefix form:

```kappa
derive lawName : P
```

declares a per-instance synthesized member. It is intentionally distinct from an ordinary member whose type happens to
end in equality. The token sequence:

```kappa
lawName : P = derive
```

is **not** synthesized-member syntax. Where otherwise legal, it parses according to the ordinary type and expression
grammars. This prevents a trailing `= derive` from being ambiguously absorbed into a member's equality type.

An instance that wants an explicit strategy, future derivation options, or a macro-generated proof writes an ordinary
definition instead, for example:

```kappa
let lawName : P = derive (P)
let lawName : P = deriveWith options (P)
let lawName : P = $(deriveMacro ...)
```

Only the first form is standardized by this patch; the latter names illustrate that ordinary right-hand-side expression
space remains available rather than being consumed by member-default syntax.

### 2.4 Amend the supertrait-context grammar

```text
supertraitContext ::= supertraitItem (',' supertraitItem)* '=>'
supertraitItem    ::= type | 'derive' type
```

Examples:

```kappa
trait Functor f => Applicative f = ...
trait derive IsSet a => Eq a = ...
trait Preorder a, derive Eq a => PartialOrder a = ...
```

In a supertrait item, `derive` applies to exactly the following type expression. A comma or the context-closing `=>`
terminates the item. Parentheses are permitted but not required:

```kappa
trait (derive IsSet a) => Eq a = ...
```

### 2.5 Amend the instance grammar

```text
instanceDecl ::=
    ['fallback'] 'instance' instancePremises? traitGoal '=' instanceBody
```

`fallback instance` is specified in §14.3.1B below. It is not a source-order priority annotation.

## 3. Equality, reflection, and function extensionality

### 3.1 Insert immediately after `Dec` in §11.4.1

```markdown
`Reflects` packages a Boolean decision with positive or negative evidence:

```kappa
data Reflects.{u}
    (parametric 0 P : Type u)
    (0 b : Bool)
    : Type u =

    IsTrue
        (proof : P)
        : Reflects P True

    IsFalse
        (refute : P -> Void)
        : Reflects P False
```

The following helpers are ordinary transparent definitions, not unsatisfied `expect` declarations:

```kappa
reflectsDec :
    forall (P : Type) (b : Bool).
    Reflects P b ->
    Dec P

let reflectsDec reflected =
    match reflected
    case IsTrue proof ->
        Yes proof
    case IsFalse refute ->
        No refute

reflectsSound :
    forall (P : Type) (b : Bool).
    Reflects P b ->
    b = True ->
    P

let reflectsSound reflected isTrue =
    match reflected
    case IsTrue proof ->
        proof
    case IsFalse _ ->
        match isTrue
        case impossible

reflectsComplete :
    forall (P : Type) (b : Bool).
    Reflects P b ->
    P ->
    b = True

let reflectsComplete reflected proof =
    match reflected
    case IsTrue _ ->
        refl
    case IsFalse refute ->
        match refute proof
        case impossible
```

The impossible branches use ordinary no-confusion for `Bool` and `Void`. `Reflects P b` is never inferred from `b` alone.
```

### 3.2 Insert immediately after `cong` in §11.4.1

```markdown
`happly` is an ordinary transparent equality combinator:

```kappa
happly :
    forall (A : Type)
           (B : A -> Type)
           (f : (x : A) -> B x)
           (g : (x : A) -> B x).
    f = g ->
    forall (x : A). f x = g x

let happly equality x =
    cong (\function -> function x) equality

happlyForall :
    forall (A : Type)
           (B : A -> Type)
           (f : forall (x : A). B x)
           (g : forall (x : A). B x).
    f = g ->
    forall (x : A). f @x = g @x

let happlyForall equality x =
    cong (\function -> function @x) equality

borrowHapply :
    forall (A : Type)
           (B : A -> Type)
           (f : (& x : A) -> B x)
           (g : (& x : A) -> B x).
    f = g ->
    forall (x : A). f x = g x

let borrowHapply equality x =
    cong (\function -> function x) equality
```

Kappa's portable foundation provides strong dependent function extensionality for ordinary and implicit quantity-`0` Pis,
and extensionality for dependent borrowed Pis:

```kappa
expect term funExt :
    forall (A : Type)
           (B : A -> Type)
           (f : (x : A) -> B x)
           (g : (x : A) -> B x).
    (forall (x : A). f x = g x) ->
    f = g

expect term forallExt :
    forall (A : Type)
           (B : A -> Type)
           (f : forall (x : A). B x)
           (g : forall (x : A). B x).
    (forall (x : A). f @x = g @x) ->
    f = g

expect term borrowFunExt :
    forall (A : Type)
           (B : A -> Type)
           (f : (& x : A) -> B x)
           (g : (& x : A) -> B x).
    (forall (x : A). f x = g x) ->
    f = g
```

At KCore, these declarations are surface projections of one binder-aware extensionality schema preserving explicitness,
quantity, observation mode, and access mode. The borrowed projection permits a dependent codomain exactly when the ordinary borrow-dependent function type is
well-formed. The theorem does not return the borrowed value or extend its region; it relates two applications at the same
borrowed argument. Nested borrowed functions are handled one binder at a time. A future revision may expose further safe
projections for additional Pi modes.

`funExt`, `forallExt`, and `borrowFunExt` are primitive proof principles of the portable foundation, or projections of a
computationally equivalent primitive supplied by `cubical-paths`. Their `expect term` declarations are satisfied by the
mandatory foundation provider, exactly as other selected foundation primitives are satisfied; they are not omitted ordinary
library implementations. Their KCore constants, provider identity, and universe schemas are part of the foundation identity
recorded by interfaces and proof artifacts.

None of these extensionality principles makes pointwise equality judgmental equality, adds function eta to conversion,
implies UIP, or implies univalence. Without `cubical-paths`, transport along a path produced by `funExt` has no additional
runtime computation rule.

The following library theorem exposes Hedberg's construction as an ordinary first-class function:

```kappa
hedberg :
    forall (A : Type).
    ((& x : A) -> (& y : A) -> Dec (x = y)) ->
    IsSet A

let hedberg decideEquality =
    derive (IsSet A)
```

The body is discharged by the standardized Hedberg provider of §14.5.6. That provider constructs a path-inductive proof
from `decideEquality`; it MUST NOT discharge this declaration by recursively applying `hedberg` itself. The generated KCore
is checked normally.

The standard equality-reflection helper is an ordinary transparent definition:

```kappa
eqReflect :
    forall (A : Type).
    Eq A =>
    (& x : A) -> (& y : A) ->
    Reflects (x = y) (x == y)

let eqReflect x y =
    match x == y
    case True ->
        IsTrue (Eq.eqSound x y refl)
    case False ->
        IsFalse (\equal ->
            match Eq.eqComplete x y equal
            case impossible)
```

`eqReflect` is not an additional required `Eq` member.
```

### 3.3 Insert an audit rule at the end of §11.3

```markdown
The use of `forall` in theorem signatures does not erase the distinction between implicit proof parameters and ordinary
computational domains.

```kappa
forall (x : A). B x
```

is an implicit quantity-`0` Pi, whereas:

```kappa
(x : A) -> B x
```

is an ordinary dependent function domain. A theorem that receives a decision procedure, comparator, function, eliminator,
or other computational argument MUST use the ordinary function type unless erased implicit application is intentionally
part of that argument's API.

H-level closure for a function type is binder-sensitive. A theorem about ordinary dependent functions concludes
`IsProp ((x : A) -> B x)` or `IsSet ((x : A) -> B x)`; it is not silently generalized from a theorem about the distinct
implicit Pi `forall (x : A). B x`.
```

### 3.4 Amend §11.5 when `cubical-paths` is inactive

Replace the statement that function extensionality is unavailable with:

```text
* the portable `funExt` principle of §11.4.1 remains available;
* it does not add a definitional equality rule or a runtime computation rule for transport;
* univalence, quotient extensionality, higher constructors, and stronger path computation remain unavailable unless an
  active extension explicitly provides them.
```

## 4. Trait evidence uniqueness and first-class construction

### 4.1 Amend §11.1.4 and §14.1.1

Replace the single justification for compiler-generated `IsSubsingleton (Tr args)` with:

```markdown
Every accepted fully applied trait evidence type `G = Tr args` remains an ordinary type and receives compiler-generated
`IsTrait G` and `IsSubsingleton G` evidence. The justification has one of two modes.

1. **Sealed-coherent evidence.** The trait declares no independent uniqueness certificate. Fresh evidence is introduced
   only through accepted instance artifacts, assumptions, intrinsic solvers, supertrait projections, or trusted boundary
   artifacts. The abstract evidence constructor and §33.2.1 coherence invariant justify subsingletonhood.

2. **Independently unique evidence.** The trait declaration contains a verified `evidence uniqueness` clause. The resulting
   certificate proves any two complete well-typed evidence values of the same trait application propositionally equal,
   independently of instance-artifact coherence. Ordinary source functions may therefore construct and return such evidence
   through the checked forms of this chapter.

This distinction affects evidence introduction and coherence justification. It does not create two trait types, change
member projection, imply runtime erasure, or change implicit-parameter syntax.

KFrontIR and interfaces record:

```text
EvidenceConstructionMode =
    SealedCoherent
  | IndependentlyUnique IndependentEvidenceUniquenessCertificateRef
```
```


### 4.2 Insert §14.1.1A after §14.1.1

```markdown
#### 14.1.1A Independent evidence-uniqueness certificates

A trait body may contain at most one clause:

```kappa
evidence uniqueness = expression
```

For:

```kappa
trait Tr parameters =
    members
    evidence uniqueness = expression
```

let `G` be the fully applied evidence type `Tr parameters` in the declaration telescope. The clause is checked against the
compiler-generated expected type:

```kappa
(left : G) -> (right : G) -> left = right
```

The binders are ordinary explicit function binders. The expression may project every member and supertrait from `left` and
`right`, use ordinary checked theorems, and invoke `derive` under the restrictions below.

The proof is **independent** only when its transitive dependency graph does not use:

* `IsTrait G`;
* compiler-generated `IsSubsingleton G` or `IsProp G` obtained from `IsTrait G`;
* local-candidate merging justified by `IsTrait G`;
* instance-artifact coherence for normalized goal `G`;
* semantic identity equality of candidate `G` artifacts;
* the uniqueness certificate currently being established; or
* an unsafe proof assertion not accepted by the active trust profile.

The proof may use independent h-level facts about member types, the appropriate binder-aware extensionality principles, path induction, no-confusion, member laws
projected from `left` and `right`, and uniqueness certificates for other evidence goals, provided the complete certificate
dependency graph is acyclic.

While checking this clause, the compiler exposes a restricted **evidence extensionality principle** for `Tr`. It accepts
proofs that corresponding supertrait slots, associated static members, and term members are equal in dependency order, with
later member types transported across earlier equalities, and returns `left = right`. This principle is generated from the
abstract evidence-record declaration itself. It does not assert any field equality, does not consult instance coherence, and
is not a public constructor, pattern, reflection API, or generic record-reconstruction operation. Outside uniqueness
checking, ordinary source continues to observe trait evidence only through its declared projections.

A successful clause produces an `IndependentEvidenceUniquenessCertificate` containing:

```text
trait constructor identity
trait parameter telescope
normalized theorem
checked proof term or checked compact certificate
ordered independent dependencies
foundation identity
provider identities and versions
unsafe/debug provenance
certificate-format version
checker version
```

The certificate is serialized in the trait interface and rechecked or independently validated when imported.

If the clause is absent, the trait is sealed-coherent. If it is present and invalid, the declaration is rejected; the
compiler does not silently downgrade it to sealed-coherent evidence.

The conventional body:

```kappa
evidence uniqueness = derive
```

asks the standardized proof engine to prove the generated theorem. It receives two arbitrary complete evidence values and
may use their projected fields. The incomplete trait constructor itself is not an implicit candidate.
```

### 4.3 Replace the portable evidence-introduction list

The portable introduction forms for a trait evidence value are:

1. an accepted ordinary or fallback instance artifact selected under §14.3;
2. an accepted local instance artifact;
3. an implicit parameter or local evidence assumption;
4. supertrait projection from accepted evidence;
5. compiler-owned intrinsic solver evidence;
6. a successful `derive` expression that either reuses existing evidence or constructs independently unique evidence;
7. an ordinary function application whose body ultimately uses only these introduction forms; and
8. a trusted boundary form whose evidence and provenance satisfy §33.2.1.

For sealed-coherent goal `G`, expression-level `derive` may resolve or transform existing accepted evidence, but MUST NOT
invent a fresh complete implementation. Fresh sealed-coherent evidence requires an `instance` or declaration-level
`derive G`, so that a coherence-governed artifact is published.

For independently unique goal `G`, expression-level `derive` may construct fresh evidence. Every generated candidate must
still typecheck; uniqueness does not establish inhabitance.

### 4.4 Relax local-instance construction narrowly

Amend the local-instance orphan restriction in §§14.3 and 30.1.1:

```markdown
A local instance whose head mentions no locally declared trait or type is additionally permitted when the normalized head
has a verified independent evidence-uniqueness certificate. Such an instance:

* participates in implicit resolution only in its lexical scope;
* may capture ordinary values and evidence by closure conversion;
* may escape explicitly only when its type, captures, and provenance are representable;
* does not become a global candidate merely because its evidence escapes; and
* is coherent with other complete evidence values by the independent certificate, not by source order.
```

This makes ordinary first-class transformations such as `hedberg` possible without allowing ordinary functions to
manufacture competing `Show A`, `Ord A`, or `Alternative f` implementations.

## 5. Supertrait and member completion

### 5.1 Replace §14.1.4 with the following additions

```markdown
#### 14.1.4 Supertraits and completion modes

Every supertrait remains a semantic refinement: completed child evidence contains one canonical projection of every
supertrait. The source context distinguishes only how the corresponding evidence slot is completed.

```kappa
trait C a => D a = ...
```

has a plain supertrait slot. Its evidence must be supplied or resolved independently of the child candidate.

```kappa
trait derive C a => D a = ...
```

has a synthesized supertrait slot. If no explicit or already-resolved coherent evidence is available, instance completion
creates a `derive (C a)` obligation that may depend on completed proper-member facets of the child candidate.

A synthesized supertrait is not weaker than a plain supertrait. After completion it is the same public projection and
participates in the same trait-refinement graph, interface identity, resolution, and coherence rules.

Explicit or directly resolved evidence has priority over synthesis. Synthesis never replaces an incoherent direct
candidate.

Trait-refinement cycles remain invalid. Completion dependencies among member and supertrait slots are checked separately
by §14.3.4A.
```

### 5.2 Replace the opening of §14.2

```markdown
### 14.2 Trait members

A trait body has four member forms:

```kappa
requiredMember : T

let ordinaryDefault : T = expression

derive synthesizedMember : T

Associated : Type
```

A required member must be supplied by the instance.

An ordinary default is elaborated once in the abstract trait context and instantiated normally.

A synthesized member creates a typed per-instance obligation. Its expected type is instantiated with the concrete instance
head, explicit instance premises, supplied members, completed dependency facets, and ordinary defaults. The instance may
override it explicitly.

Member source order is presentation order, not completion order. The compiler computes member-type and member-body
dependencies and completes an acyclic dependency graph. Runtime initializer evaluation order remains governed by ordinary
expression rules.

After explicit members and ordinary defaults, an omitted required member whose instantiated type is independently known
`IsProp` is automatically attempted with `derive`. This convenience does not apply when the `IsProp` proof depends on the
missing member, incomplete self evidence, or the candidate-merging decision being made. A failed automatic attempt is
reported as a missing member with the derivation trace attached. Automatic omitted-proposition completion uses only the
portable baseline provider profile fixed by the active language version; optional external or learned providers do not turn
an otherwise missing member into an accepted instance unless the trait author explicitly wrote a `derive` member.

A missing runtime member, associated type, proof-relevant field, or member not independently known proposition-valued is
never synthesized merely because the trait author omitted it. The trait author may opt in explicitly with the prefix
`derive` member form.
```

### 5.3 Insert §14.3.4A, “Instance evidence completion”

```markdown
#### 14.3.4A Instance evidence completion

An instance candidate is completed as a dependency graph over **facets**:

```text
instance premises
plain supertrait slots
synthesized supertrait slots
associated static members
explicit operation members
ordinary defaults
synthesized members
automatically attempted proposition members
evidence-uniqueness obligations required by generated evidence
whole evidence artifact
```

The compiler:

1. elaborates the instance head and premises;
2. records explicit member definitions without publishing complete self evidence;
3. instantiates all member and supertrait slot types;
4. adds dependency edges exposed by those types and bodies;
5. completes every acyclicly available facet;
6. invokes `derive` for synthesized slots and eligible omitted propositions;
7. checks the completed candidate against every member and supertrait type;
8. computes evidence semantic identity and exact artifact fingerprint;
9. performs the applicable coherence check; and
10. publishes the evidence atomically.

During steps 1-9, the incomplete evidence value `self : Tr args` is not in ordinary implicit scope. A completed facet may be
used directly by another facet, but a facet may not summon the dictionary currently being built and project itself from it.

Productive recursion inside an explicitly defined proof member remains available under ordinary totality checking. Merely
cycling through synthesis obligations is not productive recursion.

Top-level instance facets participate in module-wide dependency and SCC analysis. Their completion is independent of
member source order. Local instance declarations retain sequential declaration scope, but the members inside one local
instance are completed order-independently.
```

## 6. Fallback instances and the `Eq -> Equiv` bridge

### 6.1 Insert §14.3.1B after existing §14.3.1A

```markdown
#### 14.3.1B Fallback instances

A declaration:

```kappa
fallback instance premises => G = body
```

introduces a fallback candidate for `G`.

Resolution considers fallback candidates only after:

1. local implicit evidence;
2. intrinsic solver evidence; and
3. every ordinary global instance candidate

have produced no surviving solution for the normalized goal.

A well-formed ordinary candidate whose premises cannot be solved is discarded by the ordinary algorithm and does not block
fallback. By contrast, malformed candidate declarations, non-coherent surviving ordinary candidates, and ordinary-candidate
ambiguity remain errors; the resolver does not hide those errors by selecting a fallback.

Among fallback candidates, head matching, premise solving, termination, overlap, and coherence follow the ordinary rules.
If several survive, all must be semantically coherent or resolution fails with `E_INSTANCE_FALLBACK_AMBIGUOUS`. Source
order, import order, and worker completion never break a tie.

A fallback instance is recorded in module interfaces and semantic dependency closure, but it does not overlap an ordinary
instance merely because both heads can match. The fallback is dormant whenever an ordinary solution exists.

Fallback selection creates a **negative instance-environment dependency**: the selected result depends on the canonical fact
that no ordinary solution exists for the normalized goal in the effective compilation-unit module closure. That absence fact
is serialized in query and interface metadata. If a later build adds an ordinary candidate to the closure, every affected
cached or imported fallback selection is invalidated and re-resolved before its semantic result may be reused. An
implementation that cannot revalidate the absence dependency must reject the stale artifact rather than preserve the
fallback by accident of separate-compilation history.
```

### 6.2 Replace the standard bridge declaration

Keep `Eq` and `Equiv` separate. Replace the ordinary `Eq a => Equiv a` bridge with:

```kappa
-- Canonical provider/test identity: `std.prelude.eqToEquivFallback`
fallback instance Eq a => Equiv a =
    let (~=) = (==)

    let equivRefl x =
        Eq.eqComplete x x refl

    let equivSym x y p =
        Eq.eqComplete y x (sym (Eq.eqSound x y p))

    let equivTrans x y z p q =
        Eq.eqComplete x z (trans (Eq.eqSound x y p) (Eq.eqSound y z q))
```

Consequences:

* `Eq A` supplies the conventional equality equivalence when no direct `Equiv A` exists;
* a direct non-equality `Equiv A` instance is selected instead of the fallback;
* `Eq` does not require `(~=)` to agree with `(==)`;
* `Equiv` remains non-reflecting; and
* no propositional equality is synthesized from `(~=)` alone.


### 6.3 Replace §14.3.5, “Instance search termination”

```markdown
#### 14.3.5 Instance search termination

Instance-premise termination is checked over the complete ordinary-and-fallback instance dependency graph. For each
candidate edge from head goal `H` to premise goal `P`, the checker records a size-change matrix over normalized trait
arguments and the head-trait transition.

A cross-trait edge whose head-trait dependency graph is acyclic need not reduce type-constructor size. This permits lawful
bridges such as:

```kappa
fallback instance Eq a => Equiv a = ...
```

For every cycle in the trait dependency graph, the composed size-change relation must prove that:

* at least one corresponding argument strictly decreases on every traversal of the cycle; and
* no tracked argument increases in a way that can cancel that descent.

Same-trait recursion remains subject to the ordinary structural-size decrease, so instances such as `Eq a => Eq (List a)`
are accepted while `Eq a => Eq a` is rejected.

The check includes transparent normalized heads, fallback edges, generated instance premises, and supertrait-driven
resolution dependencies. It is independent of source and import order. A graph that cannot be proven well founded is
rejected with `E_INSTANCE_SEARCH_NONTERMINATING`; runtime search fuel is not a substitute for the proof.

## 9. Replace §14.5 through §14.5.1

```markdown
### 14.5 Unified derivation

`derive` requests a term of a rigid expected type. It is one elaboration protocol with several source entry points:

```kappa
let proof : P = derive
let proof = derive (P)

instance Eq T = derive
derive Eq T

derive lawMember : P
trait derive Super T => Child T = ...
```

A successful derivation produces ordinary checked KCore or a compact certificate accepted by an independent checker. It
never admits a theorem, extends definitional equality, or leaves a runtime fallback.

Conceptually, the judgment is:

```text
Gamma ; Phi ; Omega ; Rules ; Profile |- derive Goal ==> term : Goal
```

where `Gamma` is the typed lexical context, `Phi` the active proof/refinement facts, `Omega` the quantity/borrow/capture/
region/phase state, `Rules` the visible provider environment, and `Profile` the deterministic logical-cost profile. The
ordinary KCore checker remains the final typing authority for `term`.

Declaration-level:

```kappa
derive G
```

is sugar for publishing a compiler-generated instance artifact equivalent to:

```kappa
instance G = derive
```

subject to the same instance-head, termination, visibility, opacity, coherence, and interface rules.

Expression-level derivation of a non-trait type produces an ordinary term. Expression-level derivation of a trait goal:

* may return already available coherent evidence;
* may construct fresh evidence when the goal has an independent evidence-uniqueness certificate; and
* otherwise fails with `E_EVIDENCE_CONSTRUCTION_SEALED` rather than silently publishing a new implementation.

An expression-level evidence result never registers a global instance. A local binding root of trait evidence participates
in local implicit resolution by the existing lexical rule.

#### 14.5.0A Derivation outcomes

The internal result is one of:

```text
Solved(term-or-certificate, provenance)
Refuted(negation-proof, provenance)
Counterexample(checked-witness, checked-failure)
Ambiguous(candidate-summaries)
Blocked(prerequisite-obligations)
BudgetExhausted(frontier)
Cycle(obligation-path)
Unsupported(goal-class)
```

Only `Solved` accepts the source request. `Refuted` and `Counterexample` produce focused diagnostics. `Blocked` may survive
only to a specified generalization or group-completion boundary; unresolved derivation obligations never enter KCore.

#### 14.5.0B Candidate equality and ambiguity

Before reporting ambiguity, the engine:

1. removes definitionally equal candidates;
2. identifies coherent trait evidence selected under ordinary instance rules;
3. merges candidates when an independently available `IsSubsingleton Goal` proof establishes their equality; and
4. selects a deterministic representative only after such merging.

For step 3, the subsingleton proof MUST NOT depend on choosing among the candidate inhabitants being merged. In particular,
compiler-generated `IsTrait Goal` evidence may merge existing accepted trait evidence, but it does not authorize fresh
construction of sealed evidence and does not repair incoherent global artifacts.

For a proof-relevant target with two incomparable inhabitants, derivation fails. Examples include two paths `p q : x = y`
when `IsSet A` is unavailable and two constructors of an ordinary sum. `refl` is a canonical introduction when it is the
only successful plan; its existence does not automatically erase a competing higher path.

#### 14.5.1 Derived `IsSet` and `Eq`

The following remain portable:

```kappa
derive IsSet T
derive Eq T
```

`derive IsSet T` may use, in canonical provider order:

1. an existing direct coherent `IsSet T` value;
2. structural h-level closure;
3. an extension-owned checked h-level rule; or
4. Hedberg from a completed decidable equality for `T`.

`derive Eq T` jointly constructs:

```text
(==)
eqSound
eqComplete
IsSet T supertrait
```

The preferred structural provider internally constructs:

```kappa
forall (x : T) (y : T).
Reflects (x = y) (x == y)
```

and projects the public law members and Hedberg decision procedure from that certificate.

The `IsSet T` slot may depend on the completed comparator and reflection laws; those law facets may not depend on the
completed `Eq T` dictionary. The resulting facet graph is acyclic:

```text
(==) + reflection laws
        -> Dec (x = y)
        -> Hedberg
        -> IsSet T
        -> complete Eq T
```

If an explicit `derive IsSet T` request and an `Eq T` completion slot occur in one top-level semantic group, they share one
canonical goal node. Provider selection is independent of declaration order.

An invalid comparator is rejected even when `IsSet T` is independently available. Sethood does not make an arbitrary
Boolean function reflect equality.

### 10.3 Equality engines

```markdown
#### 14.5.6 Equality, congruence, and Hedberg

The equality engine has two modes.

**Set mode** is available only when the relevant endpoint type is independently known `IsSet`. Parallel path witnesses may
then be merged, union-find congruence closure may canonicalize equality classes, and proof paths may be replaced by a
deterministic representative.

**Path-sensitive mode** is used otherwise. It retains a proof multigraph, preserves parallel path witnesses, constructs
explicit `subst`, `pathInd`, `cong`, and `happly` terms, and reports ambiguity when the requested result depends on a path
choice.

The engine MUST NOT use UIP, `K`, or set-mode congruence merely because equality has one visible constructor.

The standardized Hedberg provider accepts a local decision procedure of type:

```kappa
(& x : A) -> (& y : A) -> Dec (x = y)
```

and constructs `IsSet A` by ordinary path induction. The procedure's arguments are ordinary borrowed computational inputs,
not `forall` binders. The provider identity is distinct from the public `hedberg` theorem identity so the theorem's
`derive` body cannot justify itself recursively.

### 10.4 Automatic induction

```markdown
#### 14.5.7 Automatic induction

After deterministic simplification and decision procedures fail, the induction planner considers:

* structural subjects whose constructors control recursive reduction in the goal;
* indexed subjects whose constructors refine family arguments;
* mutually recursive subjects in one verified inductive group; and
* functional induction schemes generated from checked recursive equations and termination certificates.

Before induction, the planner may generalize variables that change in recursive calls, depend on the induction subject, or
would otherwise make the induction hypothesis too specific. Generalization preserves observation mode, quantity, access,
region, capture, universe, and implicitness.

The planner records the chosen subject, motive, generalized variables, recursive equations, and induction hypotheses. It
must not choose by binder spelling or source order.

Generated recursive proof definitions pass ordinary totality checking. An external termination claim cannot justify an
induction scheme unless its certificate supplies the checked equations required by this section.
```

### 10.5 Local helper lemmas and refutation

```markdown
#### 14.5.8 Local helper lemmas and refutation

When induction is blocked by a goal/induction-hypothesis mismatch, the engine may synthesize a bounded set of strengthened
local conjectures by anti-unifying the mismatch and generalizing changing accumulators, contexts, or indices.

A conjecture is used only after it is independently proved. Before recursive proof search, the engine attempts finite
evaluation, constructor refutation, arithmetic contradiction, and other sound counterexample procedures.

Generated helpers are private to the requesting proof by default. They:

* are ordinary checked KCore declarations or local recursive definitions;
* have stable semantic identities and complete provenance;
* do not enter the ambient theorem-rule database unless explicitly materialized and annotated; and
* may be exposed by tooling for extraction into source.

A random or bounded test that finds no counterexample contributes no proof evidence.

### 10.7 Profiles, budgets, external providers, and determinism

```markdown
#### 14.5.10 Profiles and deterministic logical budgets

Portable proof acceptance never depends on wall-clock timeout. A versioned `ProofAutomationProfile` specifies deterministic

```text

maximum branching depth
maximum induction depth

Search explores plans in canonical nondecreasing logical cost. Parallelism may change latency but not the accepted result.

A learned model or LLM may rank plans only when either:

* the bounded search still exhausts the same canonical plan set; or
* the model is a pinned nonportable provider whose identity and proposals are recorded and whose resulting proof is checked.

certificate format, and checker version. Classical reasoning requires an explicit classical profile or premise; an external
classical prover cannot silently add excluded middle to portable Kappa.

#### 14.5.11 Derivation observability

Every request produces a `DeriveRecord` containing:

```text
request origin
original and normalized goal
local context summary
selected profile and logical budget
attempted provider summaries
selected plan
prerequisite DAG
generated helper identities
candidate-merging justifications
counterexample/refutation summary
generated KCore or certificate identity
exact artifact fingerprint
```

Tooling SHOULD support:

```text
show derived proof
show derivation trace
show dependencies
show generated helpers
materialize proof
extract helper lemma
minimize proof
```

#### 14.5.12 Automation quality target (non-normative)

The reference implementation should maintain a versioned automation corpus containing standard trait laws, structural
proofs, arithmetic/index obligations, h-level derivations, recursive data-structure theorems, and held-out packages.

Targets for a plain proof body consisting only of `derive` are:

```text
compiler-generated routine obligations:      at least 99 percent
standard structural and trait-law obligations: at least 95 percent
representative routine library theorem corpus: at least 90 percent
```

These percentages are benchmark goals, not a soundness rule and not a claim about unrestricted novel mathematics.

#### 14.5.13 Generic dependent inhabitation and hammer tier

After focused search, normalization, decision procedures, and induction planning, the engine may invoke a generic
dependent-type inhabitation provider. It supports higher-order goals, indexed inductive families, constructor refinement,
metavariables shared across subgoals, structural recursion, and explicit equality transport. It remains bounded by the
active logical-cost profile.

A later-cost hammer tier may combine premise selection, proof-producing superposition, SMT, and external automated theorem
provers. External tools propose premise sets, proof skeletons, or certificates; Kappa reconstructs ordinary KCore or checks a
compact certificate. Translation must preserve empty types, dependent indices, proof-relevant equality, universe levels,
and constructive/classical provenance. Unsupported translation returns `Unknown`.

The final accepted proof is dependency-minimized. An external prover's success message, process exit code, or unsafely
trusted proof trace is not evidence.

#### 14.5.14 Parametricity certificates and proof transfer

For a conservative pure, total, parametric fragment, the compiler may generate a checked `ParametricityCertificate` for a
declaration. The certificate records the declaration's relational interpretation, admitted type formers, binder observation
modes, totality and purity facts, transparency or exported equation facts, and certificate checker version.

A proof-transfer provider may use checked relations, equivalences, refinement views, newtype isomorphisms, and
parametricity certificates to transport:

* naturality and free-theorem consequences;
* representation-independence results;
* map/fold fusion laws;
* algebraic laws across certified wrappers; and
* h-level and relation-property evidence.

Proof transfer produces explicit KCore transports and does not require univalence unless the active extension and theorem
explicitly use it. Parametric quantity-`0` binders alone are not a certificate; the declaration must pass the complete
relational checker.

#### 14.5.15 Proof reconstruction and minimization

After finding a proof, the implementation:

1. reconstructs or verifies it in KCore;
2. removes unused premises and failed-branch debris;
3. shares repeated subproofs;
4. normalizes independently subsingleton proof fragments canonically;
5. chooses ordinary terms or compact checked certificates by deterministic profile thresholds;
6. rechecks the minimized result; and
7. records both semantic evidence identity and exact artifact fingerprint.

Minimization cannot introduce a theorem, erase trust provenance, replace a proof-relevant path by another without an
admissible equality, or change which instance artifact supplies an operation.
```

## 11. Expression-level `derive`

### 11.1 Insert §16.3.2A immediately before §16.3.3

```markdown
#### 16.3.2A Derivation expressions

A bare derivation expression:

```kappa
derive
```

requires a rigid expected type `G`. It requests the unified derivation judgment for `G` in the complete current lexical
context.

An explicit-goal derivation:

```kappa
derive (G)
```

elaborates `G` as a type and requests a term of that type. The surrounding expected type, when present, must be compatible
with `G` by ordinary expected-type checking.

`derive` is an elaboration form, not a term with object-language type:

```kappa
derive : (T : Type) -> T
```

No such function is introduced.

The derivation context includes every legally usable fact from:

* explicit and implicit local variables;
* branch refinements and constructor evidence;
* equalities and disequalities;
* completed local trait evidence and supertrait projections;
* completed facets of the instance candidate currently being built;
* visible transparent definitions and checked equations;
* quantity, borrow, capture, row, region, phase, and totality facts; and
* visible registered proof rules.

The context excludes:

* consumed or inaccessible values;
* mutable current-value reads not explicitly performed by source evaluation;
* hidden opaque representations;
* imported declarations not visible under the ordinary theorem-scope rules;
* incomplete self evidence; and
* facts whose only justification would be the derivation result currently being constructed.

Generated terms pass ordinary quantity and ownership checking. Derivation cannot duplicate a linear value, discard a
positive-lower-bound obligation, extend a borrow, escape a region, or use a runtime value under demand `0` merely because
the goal resembles a proof.

For a trait-evidence goal, §11.1.4's evidence-construction mode applies. A fresh sealed-coherent implementation is not an
ordinary expression result.
```

An explicitly written `derive` expression may invoke ordinary implicit resolution as a subprocedure and may invoke the full

A trait member or supertrait marked `derive`, an eligible omitted proposition member, `instance G = derive`, and

## 13. Replace the coherence-input paragraphs of §33.2.1

```markdown
Instance and evidence artifacts have two identities.

```text
EvidenceSemanticIdentity
EvidenceArtifactFingerprint
```

`EvidenceSemanticIdentity` determines source-language coherence and module semantic identity.
`EvidenceArtifactFingerprint` determines exact reproducibility, cache invalidation, proof replay, auditing, provider-version
tracking, and bytewise artifact identity.

### Independently unique evidence

For normalized goal `G` with a verified `IndependentEvidenceUniquenessCertificate`, any two complete safe evidence values:

```kappa
left  : G
right : G
```

are semantically coherent by the checked proof `left = right`. Their semantic identity is the canonical tuple:

```text
normalized goal identity
trait uniqueness-certificate identity
accepted trust-profile identity
```

rather than the normalized syntax of one candidate implementation. Their exact terms, generated proofs, captured values,
providers, and provenance remain in their artifact fingerprints.

The certificate does not make an ill-typed or incomplete candidate valid. Each candidate is checked before the uniqueness
proof is applied.

### Sealed-coherent evidence

For a sealed-coherent goal, complete concrete artifacts continue to be compared by the ordinary Easy-Hash / `HardIdentity`
algorithm. A fresh expression cannot create another artifact outside the permitted evidence-introduction forms.

### Subsingleton fields

For either mode, the semantic input includes every source-observable projection:

* runtime methods;
* associated static members;
* supertrait evidence;
* law and proof field types;
* law and proof inhabitants when their exact field types are not independently subsingleton;
* compiler-generated evidence fields; and
* intrinsic facts affecting those projections.

If safe independent evidence establishes `IsSubsingleton F`, a field value of type `F` contributes a canonical
subsingleton marker rather than its exact proof syntax. The marker records the normalized field type and the independent
h-level justification. `RuntimeErased F` alone is insufficient.

Compiler-generated `IsTrait F` may justify equality of already accepted local trait evidence, but it cannot be used
circularly to accept incoherent global artifacts or to prove an evidence-uniqueness certificate for `F`.

### Provenance and trust

Equality of semantic evidence does not erase provenance. Exact artifact fingerprints retain:

```text
complete generated KCore or certificate
provider identities and versions
foundation identity
selected theorem and evidence dependencies
captured values and closure-conversion identities
unsafe/debug ledger
external transcripts
```

A safe result and an unsafe asserted result may be propositionally equal yet have different trust provenance. A build that
does not accept the latter's trust boundary cannot import it merely because an equality proof exists.

### Coherence algorithm

1. Typecheck every complete candidate independently.
2. Partition by normalized trait goal and accepted trust profile.
3. If the goal is independently unique, verify the uniqueness certificate and accept all complete candidates as one
   semantic implementation, selecting a deterministic representative for projection and code generation.
4. Otherwise apply the ordinary Easy Hash and `HardIdentity` algorithm.
5. Never use exact artifact fingerprint equality as a substitute for a failed semantic coherence check.

Representative selection among coherent candidates follows canonical provider/module/origin ordering and does not affect
source-language semantics.
```

Where §33.1 serializes an instance contribution into declaration or module semantic identity, it serializes
`EvidenceSemanticIdentity`. Exact build artifacts additionally serialize `EvidenceArtifactFingerprint`.
